# 全页面加载审计（2026-08-11）

## 覆盖范围

本台账覆盖 `frontend/src/App.tsx` 注册的全部业务路由，以及同一路由内会切换并首次取数的标签页。重定向路由 `/post-delivery`、`/shipping/:issueId` 不重复计数。

- 33 个可进入的业务路由/路由变体全部核对。
- 28 个路由进入时会读取业务数据；5 个路由进入时仅渲染静态表单或导航。
- `/finance` 另有 3 个首次取数的标签页；合同页也区分渠道与合同两个标签。
- “SQL 上限”是页面首屏各并发接口中的最大串行查询数，不是把并发接口简单相加。公网 MySQL 下，它比请求总数更接近用户实际等待时间。

## 全局根因与处理

1. 首次进入多请求页面时只预热了一条连接，其余请求现场创建公网 MySQL 连接。现在启动时并发预热 6 条核心连接，默认池大小 10、溢出 20。
2. `pool_pre_ping=True` 让每个请求先额外执行一次公网 SQL。连接一小时回收已低于常见 MySQL 空闲超时，因此关闭逐请求 pre-ping。
3. 路由 chunk 只在首次点击时下载。登录后等待 10 秒，再以每批 4 个的方式预取业务路由 chunk，避免与当前首屏数据竞争。
   印数 Dashboard 的简单折线图改为原生 SVG，生产 chunk 从约 1.15 MB 降到约 15.2 KB。
4. `/auth/me` 在开发 StrictMode 下可能重复。现在同一次挂载去重，并缓存验证结果 5 分钟。
5. TanStack Query 默认 `staleTime` 提升到 2 分钟；业务入口和目标页面统一 query key，避免刚在入口读取、进入模块又重新读取。
6. 所有 API 的 `Server-Timing` 同时返回 SQL 次数、SQL 耗时和应用总耗时；开发环境控制台输出对应性能日志，后续新增页面可直接发现回退。

| 邮局投递 | 5 SQL / 3.99s | 2 SQL / 1.57s |

## 回归边界

- 列表行数增加不得增加 SQL 次数；历史期数、合同、渠道结算和刊期表已有固定 SQL 数量测试。
- 页面首屏不得重新拆成多个重复统计请求；营销交易入口使用 `/api/orders/portal-summary`，订单列表使用 `include_view_counts=true`。
- 简单趋势图保持原生 SVG，不要为单个折线图重新引入完整 ECharts 运行时。
- 数据写入后继续使用现有显式缓存失效，不能只依赖 TTL。
- 若预热后仍要求所有重页面稳定进入 1 秒内，需要把应用与 MySQL 迁到同地域内网或增加受控连接代理；应用层无法消除公网单次 SQL 的物理往返。
