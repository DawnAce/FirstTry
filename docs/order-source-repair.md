# 销售来源历史数据修复

代码入口已统一销售来源及去重。存量数据使用单独的只读预览与显式执行命令修复，不能靠直接 SQL 改名或删除重复订单。

## 生成预览

在 backend 目录使用当前虚拟环境：

```bash
python scripts/repair_order_sources.py --preview ../backups/order-source-repair.json
```

MySQL 预览在只读一致性事务中运行，不提交业务修改。预览文件只包含记录 ID、平台／店铺、差异字段和关联计数，不包含真实姓名、电话、地址或来源单号；默认文件权限 0600，禁止加入 Git。目标文件已存在时拒绝覆盖。

预览包含：已知别名及空店铺的标准化清单、规范身份重复组、来源原件身份冲突、预计保留主单及全部关联的状态签名。主单建议优先已有邮局记录的一单，其次唯一手工单；建议不是自动决定。未知平台／店铺不擅自合并，来源原件规范身份冲突需要单独处理。

## 核对重复订单

通过预览中的订单 ID 在系统中核对日期、金额、订期、收件资料及邮局关联。逐组填写 resolutions：明确 keep_order_id、其余 duplicate_order_ids，并在核对后将 keep_business_fields 改为 true。这表示保留主单的全部业务字段，不从重复单覆盖日期、金额、地址或订期。

被停用的重复单只允许存在未绑定明细／目标的订阅原件关联。若有财务、邮局、发货、投诉、运费、退款或目标级关联，整批阻断，需要另行核对迁移。来源原件身份冲突也阻断，不能自动合并原始版本。

## 执行与核验

生产执行须先获得对具体变更清单的明确确认。由管理员操作人执行：

```bash
python scripts/repair_order_sources.py --apply ../backups/order-source-repair.json --operator 管理员用户名 --reason '已逐笔核对，保留主单业务资料及邮局关联'
```

执行时重新加锁、检查状态签名及所有关联，预览后任何相关变化都要求重新预览。整批事务：标准化订单／来源身份、将旧关联置为无效并新增主单关联、作废重复单、追加订单／来源／通用操作日志；不硬删除订单、明细、履约版本、邮局记录或原始版本。相同已完成预览重复执行返回原结果，不再次写入。

核验应检查：未作废订单不再存在相同规范身份；来源原件数量与版本内容保持不变；旧关联仍可审计，新有效关联落到保留主单；邮局、已发货、收退款及发票记录不改变。总订单记录数不减少，生效重复单数量减少。原件的 revision 不因身份标准化增加，lock_version 增加使旧预览失效。

失败会完整回滚。成功后的撤销不能通过删审计或盲目回放原值完成；须依据 repair_id 及前后事件另行预览核对，特别是修复后已发生新业务时。
