# 电商订单导入结果：分类边界与判定依据

核对日期：2026-09-11。基于来源交易功能简化页面分类，适用于 CBJ 小程序和淘宝订单。

商业状态、导入结果和发货资格是不同概念。当前页面有五类结果；后台保留六种处理动作，其中 `import`（建单）和 `retain`（仅保存交易）统一显示为“可导入”。只检查底层建单函数的四类中间结果，会遗漏来源处理阶段。判断真实订单是否识别有误，须核对原始状态、平台/店铺/单号、已有来源原件、商品、日期及该行最终原因，不能只凭截图中的状态文字。

## 1. 五个结果标签的边界

| 页面标签 | 最终条件 | 确认后结果 | 处理方式 |
|---|---|---|---|
| 可导入 | 通过建单检查，或无已有来源时的纯运费、已有业务订单补原件 | 建单并保存来源；纯运费和补原件仅保存交易 | 后两种在行内注明“仅保存交易”，不新增订阅或发货。核对明细和警告，必要时到来源交易关联订阅或核对费用 |
| 来源更新（行内“来源更新待核对”） | 相同平台、店铺和单号的来源已存在，本次内容有变化 | 逐笔确认后保存来源新版本，保留旧版本 | 点开核对前后信息；不自动回写主订单状态、财务或投递 |
| 重复 | 相同平台、店铺和单号的来源已存在，内容未变化 | 不重复建单，不新增来源版本 | 通常无需处理；只有业务订单、尚无来源原件时，归可导入，仅补充原件 |
| 待确认 | 未被来源规则接收，且缺可用下单/支付日期、无可识别商品行，或商品识别未通过；退款和部分退款同样处理 | 不建单、不保存该行来源；同批其他可处理记录仍可确认 | 按该行原因处理后重新预览；缺日期不能靠随意新增商品解决 |
| 跳过 | 未被来源规则接收，且命中待付款、取消/关闭或整单忽略商品规则 | 不建单、不留存该行 | 核对排除原因；源状态或忽略规则有误时先纠正依据 |

**“跳过”仍有独立意义，应保留：它表示规则排除；“重复”表示来源内容不变；“待确认”表示未解决的建单问题。** 跳过不是所有“没有新建业务订单”的总计，也不包含仅保存交易的记录和来源更新。

五类互斥，**全部 = 可导入 + 来源更新 + 重复 + 待确认 + 跳过**。全部是成功解析的记录数，不等于 Excel 物理行数（空来源单号等会被解析器略过）。文件/必需表头解析失败、同一文件重复来源单号属于接口报错，不进入这五类。

分类只筛选显示。确认始终处理整批可导入记录和来源更新；任何一笔来源更新未确认，或任一待建明细的不确定期号未核对，都会阻断整批提交，失败不留下部分写入。「期号待核对」是辅助筛选，不新增导入结果分类；对应记录仍计入可导入。

## 2. 判定顺序：先建单资格，再来源交易

第二阶段可以改变第一阶段结果；页面将最终动作中的 `import` 和 `retain` 合并展示，其余动作各对应一个分类。

**第一阶段（`build_import_preview`）按顺序短路检查：**

1. 待付款、取消/关闭 → 初步跳过；退款和部分退款继续检查。
2. 同来源单号、店铺及平台范围内已有业务订单 → 初步重复。兼容平台为空的旧订单，不限草稿、生效或作废状态；不同平台/店铺不会仅因单号相同而排除。
3. 先用下单日期，否则用支付日期；两者都缺 → 初步待确认。
4. 移除运费行及忽略商品。没有剩余商品且移除了忽略商品 → 初步跳过；没有商品也没有忽略商品 → 初步待确认。
5. 有效商品逐行匹配商品库或商学院单期规则，任意一条仍不匹配 → 初步待确认。
6. 其余生成待建单数据 → 初步导入。

**第二阶段（`preview_import`）依次决定最终动作：**

1. **已有相同平台/店铺/单号的来源**：原件有变化 → 来源更新；无变化 → 重复。此分支优先于初步状态、日期和商品结果。换文件名、工作表名或行位置不单独制造变化。
2. **无已有来源，且为纯运费**：`retain`，页面为可导入，仅保存交易。包括待付款、取消、退款或缺日期的纯运费；保留原始状态，不表示费用已核实。
3. **无已有来源，但初步重复**：`retain`，页面为可导入，仅补原件，不重复建业务订单、不覆盖人工修改。若同时已取消，第一阶段先跳过，不走此分支。
4. **其余保持初步结果**：导入、待确认或跳过。退款/部分退款商品未知、缺日期、空商品时保持待确认，保留具体原因和未识别商品名，供当前页处理。

因此，“已有来源＋已取消”先比较原件；“只有已有业务订单＋已取消”仍跳过；“退款＋忽略商品＋日期有效”跳过，但“退款＋忽略商品＋缺日期”保持待确认。修正数据后重新预览可能进入另一个分支，每次仍只计一类。

## 3. 退款状态的交叉情况

下表未注明已有来源/业务订单的记录均为新交易；未注明缺日期的记录均有可用日期。

| 输入情况 | 最终结果及原因 |
|---|---|
| 已退款或部分退款，商品可识别、有日期 | 可导入，业务订单保留退款状态 |
| 退款，商品无法识别 | 待确认，可关联已有商品或新增商品后重新识别 |
| 退款，缺少下单和支付日期 | 待确认，补齐日期后重新预览 |
| 退款，只有运费行 | 可导入，注明纯运费记录，仅保存交易，不生成投递 |
| 退款，已有同范围业务订单但无来源原件 | 可导入，仅补原件，原订单状态不因重导改变 |
| 退款，已有同一来源且内容不变 | 重复 |
| 已有同一来源由已发货变为退款 | 来源更新，逐笔确认后保留新原件；主订单仍须另行处理 |
| 退款，有日期且整单商品都在忽略名单 | 跳过，原因是商品规则 |

新退款订单的未知商品进入待确认汇总及商品关联入口。若先确认同批其他可导入记录，该退款行不会被保存成来源、也不会变为重复；保留原文件，补齐别名后再次上传即可识别并建单。只有待确认、重复和跳过时，确认按钮禁用。

导入退款记录不等于新执行退款、核实退款金额或允许继续发货。来源状态更新也不等于主订单退款状态同步。

## 4. 警告及其他例外

- **缺订期、往期期号或商学院期次**：当前可先导入，部分情况有警告，之后补录；与缺下单/支付日期不同。“最新一期”因付款时间或刊期表不足而无法判期时，须按下一条完成核对。
- **最新一期的不确定期号**：翻期临界、付款时间缺失或刊期范围不足的待建单期明细，必须在提示下确认建议期号，或从刊期表中改选实际期号并确认。分类仍为可导入；整批提交前须全部完成，核对结果连同建议依据入审计。已有来源的重复/来源更新不建业务订单，不要求核对业务期号。
- **无法识别的状态**：先匹配已知值，再按关键词兜底；仍无法识别时，当前默认已付款并标记未知。通过其他检查的新订阅记录仍归导入，不因警告自动转待确认，确认前必须核对原始状态。
- **忽略商品**：关键词为“家族企业、深潜、深度系列、电子刊、对公专用、利润薄如刀片”。混合订单仅移除命中行，其余继续识别；出现一个忽略商品不代表整单跳过。
- **警告不一定改变分类**：转中通、缺往期期号等提示不自动变成待确认；翻期临界同样保持可导入，但须完成显式期号核对才能提交。最终结果不是所有数据质量问题的分级。
- **旧版已留存的来源补齐商品**：重导有变化会进入来源更新；该流程仅更新来源，不自动转建业务订单。不要把重新识别或来源更新理解成已完成订阅建单。

## 5. 预览计数与确认结果

API 字段和处理动作保持兼容，`counts.import` 仍只计待建订单，`counts.retain` 仍只计纯运费和补原件；页面“可导入”计数及筛选为两者之和。确认按钮按“笔”统计，摘要列出新建订单数和仅保存交易数。会话分别保存可建单行及可保存/更新的来源。确认时再次检查业务订单和来源版本，防止预览后数据变化。

- `created` 只统计新建业务订单；`retained_sources` 只统计本次新增的留存来源，不包含来源更新或随新订单保存的来源。
- `skipped_duplicates` 只统计待建单行在确认时新增发现的业务订单重复，**不包含预览“重复”计数**。
- 所以“预览重复 2、确认提示跳过重复 0”不表示重复订单被导入；仅有来源更新时，新建订单数和新增交易记录数均为 0，也不表示更新未保存。
- 仅有重复、待确认和跳过时，页面不能确认；存在可导入记录或来源更新时可进入确认，但来源更新必须逐笔勾选、不确定期号必须逐明细确认，且并发校验须通过。

## 6. 实现与验证

- 状态映射：`backend/app/services/order_import_status_service.py`。
- 两阶段分类、计数、预览会话和原子确认：`backend/app/services/cbj_order_import_service.py`。
- 来源身份、原件比较、版本与确认：`backend/app/services/order_source_service.py`。
- 页面将后端 `import` / `retain` 合并为可导入：`frontend/src/pages/OrderImport.tsx`；共享说明：`ecommerceRules.tsx`。
- 专项回归：`backend/tests/test_order_import_decision_boundaries.py`，覆盖两阶段交叉规则、状态/日期/商品、来源重导优先级、平台店铺范围及合成 Excel 预览→确认；核对六种后台动作互斥、未确认来源更新阻断整批、来源版本留存和已有订单不被修改，并覆盖 CBJ / 淘宝全额与部分退款先待确认、补别名后再次预览确认的闭环。前端 Storybook 覆盖合并筛选和计数、整批提交、待确认退款商品入口、亮色舒适及暗色紧凑。

测试使用 SQLite 内存库和合成订单，CI 另验证后端全量及空 MySQL 迁移链。这些验证不替代真实订单原始数据核对，也不穷尽自由文本状态与商品名称。本次移除新退款订单的强制留存分支，并合并页面分类，不改变数据库结构或已有来源记录。来源功能见 [订单来源交易](order-source-transactions.md)。
