# 渠道结算结构化周期与退报设计

日期：2026-08-05

## 目标

把结算从“自由文本周期 + 单一应结金额 + 单附件”升级为可识别、可查询、可核对的长期档案，同时兼容已有记录。

## 核心决策

- 一条系统记录对应一张外部结算单，而不是强制按每个周次拆行。
- 结算周期和退报周期均保存开始/结束日期；单周时两端相同，不限制星期几。
- 正常总额与退报扣款分开保存，净应结由后端计算。
- 结算方向显式区分应收与应付，界面据此切换收付款及销项/进项措辞。
- 渠道开票资料属于 `Partner` 主数据，结算单只保存本次快照字段。
- 附件改为一对多并分类；Excel 结算单是一等附件类型。
- 系统编号和外部编号分离：系统编号按渠道/个人自动生成且不可编辑，外部平台编号允许为空和重复。
- 北京报零新增代销/包销；XLSX 按标题和表头识别，正数为正常结算、负数为退报，预填后由用户确认。
- 新建页把“先上传结算凭证（可跳过）”放在基础信息之前，形成上传 → 识别 → 核对/补全 → 保存的顺序；保存时通过 multipart 一次性提交，文件和数据库记录要么同时成功，要么同时回滚。
- 发票附件是开票完成的事实依据：上传后自动已开票，删除最后一份后回退；收付状态单独保存。
- “代销/包销”改称销售模式，并由渠道档案配置为不适用、选填或必填；北京报零必填，其他渠道默认隐藏且保存为空。
- 新增弹窗只负责建单，不承载开票、收付款和手工状态。保存后的详情抽屉分别提供附件、开票、收/付款和操作记录。
- 附件按文件独立推荐和修改类别，识别反馈必须明确归属文件；多份结算单只能指定一份主结算单驱动回填。
- 识别只补空字段或仍由上一轮识别控制的字段；用户一旦人工编辑即获得优先权，后上传或切换主表不得静默覆盖，并要在文件下列出“已自动填入/已保留人工填写”。
- 结算对象查询区分加载失败与真实空数据；失败时提供重试和迁移提示，空数据时引导先维护合作渠道。
- 登记发票必须留存发票文件并更新开票状态；收/付款按次累计登记。两套状态独立，兼容主状态由动作派生。

## 兼容策略

- `period`、`attachment_filename`、`attachment_path` 暂不删除。
- 迁移把旧附件复制到新附件表，旧接口继续可用一个版本周期。
- 历史结算默认 `payable`，维持旧版“付款/进项发票”语义。
- 新页面只写结构化日期；历史自由文本在列表中回退显示。
- 迁移为历史记录补 `JS-QD-YYYYMM-流水号`，旧 `settlement_no` 复制到 `external_no`，不丢失原值。

## 校验

- 起止日期必须同时存在且开始不晚于结束。
- 有退报扣款必须有正常总额和退报周期。
- 系统结算单号全局唯一；外部平台单号只提醒不强制唯一；关联合同必须属于所选合作方。
- 金额使用 `DECIMAL`，前后端以字符串/数字载荷传输，计算在后端复核。
- 附件扩展名白名单和 20MB 大小限制前后端双重校验。
- 同一结算内按 SHA-256 拒绝重复附件；识别失败仍允许人工填写和保存原文件。
- 明细合计、正常金额减退报扣款与应结金额不一致时显示告警，不静默覆盖用户确认值。
