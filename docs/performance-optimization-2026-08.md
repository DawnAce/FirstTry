# 发行系统性能优化记录（2026-08）

## 背景与结论

生产数据量不大，页面慢的主要原因不是表规模，而是应用连接公网 MySQL 后，每一次连接和 SQL 往返都很昂贵。优化前首次连接约 13 秒，复用连接上的单次查询也常需 0.6–2.3 秒；因此逐行查询和页面并发请求会被网络延迟成倍放大。

本轮保持业务口径不变，优先消除 N+1、重复请求和不必要的连接创建。数据库迁移不在本轮范围内。

## 基线与复测

| 场景 | 优化前 | 优化后 |
|---|---:|---:|
| 刊期列表（历史印数期数） | 9 期共 20 次 SQL；HTTP 约 11.9 秒 | 1 次 SQL；远程数据库复用连接约 0.61 秒，登录页面完整显示 9 期约 1.83 秒 |
| Dashboard | HTTP 约 15.2 秒 | 3 次 SQL；复用连接约 1.6 秒 |
| 订单列表 | 2 单共 9 次 SQL；页面 7 个并发请求，约 9.1 秒 | 列表和六个视图数量合并为 1 个请求、约 3 次 SQL；HTTP 抽样约 3–6 秒 |
| 报数确认 | 保存后确认两次请求；32 条明细逐条查询 | 当前值随确认一次提交；明细一次加载并在同一事务更新 |

远程网络存在明显波动，上表时间用于判断数量级，不作为 SLA。SQL 次数是更稳定的回归指标：列表行数增加时，查询次数不应线性增长。

## 已落地的优化

### 后端

- 历史印数期数列表将刊期、年内期次、计划版数和印数合计合并为一次数据库查询；查询次数不再随刊期数增长。
- Dashboard 一次加载出版计划，在内存计算年内期次、计划版数和下一期。
- 订单列表批量加载刊期、商学院刊期和发货进度；`include_view_counts=true` 时，列表、分页总数和六个状态数量共享一次聚合。
- 保留 `GET /api/orders/view-counts` 作为兼容接口；发行系统前端使用合并后的订单列表响应。
- 邮局投递批量诊断订单、明细和最新收件目标；概览的份数、单位数、缺失数和最近到期日合并为一次聚合。
- 报数确认可接收当前 `entries`，保存、校验、快照和确认在同一事务完成。
- 已认证用户缓存 30 秒并防止并发缓存击穿；连接池使用 LIFO、1 小时回收和 pre-ping。
- 大响应启用 GZip。所有 API 返回 `Server-Timing: app;dur=...`；超过 2 秒记录 `slow_api` 日志。

### 前端

- 所有页面组件按路由懒加载，进入页面时只下载所需 chunk。
- TanStack Query 默认 `staleTime` 调整为 60 秒、`gcTime` 调整为 10 分钟。
- 订单页从六次状态计数加一次列表请求，收敛为一次合并列表请求。
- ZTO-MF 单期详情只请求一次全量明细，筛选和公司选项在本地派生，重试不重复刷新同一资源。
- 报数确认直接提交编辑器中的当前值，不再先调用独立保存接口。

## 接口与运维约定

- `GET /api/orders?include_view_counts=true` 的响应除 `rows`、`total` 外还包含 `view_counts`：`all`、`active`、`pending_confirmation`、`draft`、`attention`、`void`。
- 角色或用户删除最多需要 30 秒反映到已登录请求，这是认证缓存的明确边界。
- 观察慢请求时先看 `Server-Timing` 和 `app.performance` 日志，再区分数据库冷连接、SQL 往返和前端资源加载。
- 不要把批量序列化重新改成循环内查询，也不要恢复订单页的多状态并发请求。
- 若目标是稳定 1 秒级，优先将后端与 MySQL 放在同地域内网，或使用受控的数据库连接代理；应用层继续堆缓存无法消除公网握手延迟。
