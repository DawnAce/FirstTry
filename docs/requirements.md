# 需求文档

## 1. 项目背景

《中国经营报》是一份周出版的财经报纸，周五需要生成下周一出版的印数管理表和中通快递发货明细。

### 1.1 业务痛点
- 周手工填写 Excel 报数表，容易出错
- 发货名单管理混乱，订阅状态难以追踪
- 固定数据和变动数据混在一起，效率低下
- 历史数据缺乏系统化管理

### 1.2 解决方案
开发一套 Web 应用，实现：
- 自动生成报数表和发货明细
- 分离固定数据和变动数据
- 管理收件人和订阅信息
- 导出符合规范的 Excel 文件
- 将每期报数来源 PDF / 图片作为原始凭证归档，识别后由人工确认写入
- 将成都杂志铺跨月补发拆分为结算调整和补发执行，且不改动已出刊印数
- 用户认证和权限管理（管理员/操作员）
- 确认锁定与作废审计追踪

## 2. 2026年刊期表

### 2.1 基本信息
- **总周数**：52 周
- **出版期数**：49 期
- **休刊期数**：3 期
- **期号范围**：2635 - 2683

### 2.2 休刊日期
1. **2026年2月16日**：春节休刊（不占用期号）
2. **2026年2月23日**：春节休刊（不占用期号）
3. **2026年10月5日**：国庆节休刊（不占用期号）

### 2.3 出版规律
- 周一出版（除休刊日）
- 周五完成下周的报数和发货准备
- 期号连续递增，休刊周不占用期号

### 2.4 年度刊期表维护
- 管理员可以上传年度刊期 PDF，系统解析出版日期、期号、休刊信息和版数（从"对开XX版"提取）。
- 管理员可以在「刊期表管理」页面按年份查看年度计划摘要、按月份分组的刊期表和上传记录。
- 上传后必须先预览解析结果；只有校验无误的结果才能提交写入正式刊期表。
- 预览行应支持手动新增、删除和修改出版日期/期号/休刊状态，版数可在预览统计区域手动编辑，并在保存前重新校验。
- 非休刊行期号必须连续递增；休刊周不填写期号，也不消耗期号。
- 系统需要保留上传记录、解析摘要、错误信息、上传人和提交时间，便于审计。
- PDF 解析失败、依赖缺失或抽取到无法匹配的日期数字时，系统应给出可理解的错误提示，不应写入正式刊期表或返回未处理的 500。
- 已创建期数受保护：更新年度刊期表时，不得删除已创建期号，也不得修改已创建期号的出版日期。
- 支持文字版 PDF；扫描 PDF 需要先 OCR 成可抽取文本后再上传。

## 3. 周工作流程

### Step 1: 创建新期
- **时间**：周五
- **操作**：点击"创建本期报数"按钮
- **系统行为**：
  - 自动识别下一个期号
  - 自动获取对应的出版日期
  - 优先从上一期复制报数项目；如果是第一期，则从模板初始化
  - 固定项沿用上一期或模板默认值
  - 变动项沿用上一期或模板默认值，等待本期调整
  - 首页仪表盘展示统计卡片（总期数、待处理、本周印数与上周对比、最新报数时间）、一键创建、补录其他期数、报数流程指引、最近 5 期印数表格和对应的 ECharts 趋势图；补录下拉项必须以 `第 X 期（出刊日期：YYYY-MM-DD）` 展示刊期表中的完整出刊日期；趋势图纵轴从 4,000 份起

### Step 2: 输入变动数据
- **时间**：周五上午
- **操作**：在报数编辑页面填写橙色高亮的变动项
- **版数**：页面顶部同时显示「计划 XX 版」（来自期刊表）和「实际 XX 版」。创建期次时自动从期刊表获取计划版数作为初始值，确认前可手动修改；不一致时显示警告。版数会影响导出的 Excel 报数表
- **计划与实际分离**：历史印数导入只更新 `Issue.page_count`（实际版数），不得覆盖 `publication_schedule.page_count`（计划版数）
- **期次上下文**：报数页的期次、日期、状态和操作按钮作为一个完整页头固定在全局导航下方；纵向滚动录入、核对来源或查看历史时，当前处理期次必须持续可见
- **社用报收发室自留合计**：社用报区域应在保留原录入样式的前提下，只读实时汇总《社用报分发表》口径的营报传媒（收发室）、中经传媒智库至库房的 12 个常规部门及临时加印自留；显示是否为 5 的倍数和按 50 份/捆计算的参考捆数。14 项计算明细默认折叠，不提供第二套输入或保存逻辑，任何修改仍以页面原有报数项和临时加印归属明细为唯一数据源
- **变动项包括**：
  - 北京邮发（外埠）
  - 北京邮发（本市）
  - 北京报零（东部）
  - 北京报零（西部）
  - 广州日报（零售）
  - 广州日报（订阅）
  - 临时加印（支持归属明细分配）
  - 营报传媒
  - 财经中心
  - 备用报

**原始来源与自动识别**：
- 北京邮发、北京报零、广州日报按每周来源文件上传；成都杂志铺按月度整月图片上传。
- 支持 PDF、JPG、JPEG、PNG。原文件必须先保存，再进行 OCR 和渠道模板解析；同一渠道相同文件应去重。
- OCR 结果只是建议值。页面必须展示原始值、拟写入值、识别警告和刊期映射，由用户确认后才允许写入草稿报数。
- 北京邮发的业务映射为：本市来源数 + 损失 20 份的一半、外埠来源数 + 另一半。仅当损失确认为 20 份时才按各 10 份分摊；手写合计无法可靠识别时必须提示人工核对。
- 成都月度文件可一次关联当月多期。来源中标记“待确认”的刊期保留 `channel_pending` 状态，在该期创建或确认时继续提醒。
- 已确认的月度来源可以先关联尚未创建、但已存在于刊期表的未来期；未来期创建后自动带入已人工确认的数值。
- 同一份周度 / 月度来源可以同时关联不同状态的刊期。提交映射时服务端逐期锁定并复核状态：草稿期按基础 / 印前追加来源写入；已确认或已导出期自动转为「仅归档凭证」，印数、结算和补发增量均为 0，不能因整份文件跨期而拒绝草稿期写入。
- 报数确认必须按本期明细判断来源状态：本期 `OCR待核对` / `渠道待确认` 或上传于本期但尚无本期映射的文件继续阻断；同一跨期文件仅其他期待处理时只提示，不得阻断本期已核对报数。对未完成的同一文件点击「继续核对」必须保留各明细原有的基础 / 追加 / 归档用途并可幂等提交，不得把文件自身误判为第二份基础来源。
- 每份来源必须独立保存其有效贡献。首份为基础，确认报数前的后续文件可作为印前追加；当前印数等于所有有效基础 / 印前追加贡献之和，不允许“最新上传覆盖之前来源”。
- 「重新上传」是文件级定向替换：新文件继承被替换文件的基础 / 追加角色，旧文件标记已替换且不再参与计算，其他有效来源保持不变。确认前必须展示原贡献、新贡献及总数变化。
- 已确认来源的原文件无误、仅人工核对数字填错时，草稿期必须提供「更正核对数字」而不要求再次上传文件。更正沿用原归档文件建立新的不可变核对版本，期号、项目和核对状态不可随意改动；提交时新明细定向替换旧贡献，旧记录保留为「已替换」，并写入更正及确认审计日志。普通上传仍按渠道和 SHA-256 去重。
- 报数确认后，后续图片进入「确认后凭证」，不修改锁定印数；仅补充来源证明时可选择「仅归档」且不影响任何数量，追加订数影响结算和补发，补损只影响补发，冲减只影响结算。

### Step 3: 确认报数
- **操作**：点击"确认报数"按钮
- **实时一致性预警**（确认前即可见）：
  - 报数编辑页与 ZTO-MF 当期 Tab 顶部，只要"中通物流公司"报数合计 ≠ 当期发货明细合计，就显示黄色 ⚠️ Alert 提示差值
  - 草稿阶段也会显示，鼓励用户尽早调整，避免最后一刻才发现对不上
- **系统验证**：
  - 所有变动项必须有值
  - 数值不能为负
  - 总印数不能为 0
  - 当期已上传来源中不能存在 `OCR待核对` 或 `渠道待确认` 项
  - 北京邮发、北京报零、广州日报、成都杂志铺存在已人工确认的有效印前来源时，逐个 `类别 / 子项` 比较来源确认值与当前印数；任一项目不一致即阻止确认，即使渠道合计碰巧一致也不能通过
  - 报数去向"中通物流公司"合计与当期ZTO-MF份数合计不一致时，确认接口返回核查提示
- **结果**：
  - 状态变更为 `confirmed`
  - 所有数值显示为纯文本（只读），无法再编辑
  - 当期没有非固定ZTO-MF计划时，自动从上一期复制非固定明细作为本期起始数据，并清空确认状态和发货时间，供人工调整；`recurring_generated` 固定明细不视为完整计划，也不得从上一期重复复制
  - 确认记录保存到修订历史
  - 确认事务或操作日志写入失败时保持 `draft`，前端明确提示“本次报数没有确认成功”，不得让用户误以为已经锁定
  - 系统额外保存一条确认快照，记录确认时的报数中通合计、发货明细合计、差值和是否一致
  - 报数编辑页与ZTO-MF页都可查看"确认时快照"与"当前明细状态"，用于识别确认后漂移
  - 上面提到的实时 ⚠️ Alert（草稿期预警）与"确认时快照"（确认后漂移追溯）并存，作用阶段不同

**作废机制**：
- 管理员可以在报数编辑页面点击"作废"按钮撤销确认
- 可填写作废原因（可选）
- 作废后状态重置为 `draft`，可以重新编辑和确认
- 所有确认和作废操作记录在 `report_revisions` 表中，形成完整的审计追踪

### Step 4: 检查发货明细
- **操作**：进入「物流管理 → ZTO-MF」
- **系统行为**：
  - 该页作为当前期中通执行明细的唯一维护入口
  - 用户按期号查看、筛选、维护 `shipping_details`
  - 页面显示当前发货总份数，以及确认时快照/当前状态/是否漂移
  - 顶部保留两条独立状态：发货计划对账按“确认报数 = 当前计划 + 已归因停发”计算未解释差异；确认时发货明细快照只用于显示确认后漂移，不把已经与确认报数一致的当前计划标成异常。实际发货与核销分别统计实际寄出、无需发货、转库留存、待每月两次合寄、待月底合寄和未解释待补，桌面端每条状态保持一行
  - 运单文件中已解析但未匹配的行必须完整保留并突出展示，不得在确认导入时静默丢弃；确认后仍可人工关联
  - 标题含“高铁”的运单工作表按专用列布局解析：展示名称不作为收件人，实际姓名、电话、地址、份数和运单号必须进入正常自动匹配流程
  - 同一条计划明细被拆成多个运单时，支持把多个运单批量关联到该明细，并为每个运单建立独立包裹记录
  - 导入结果必须区分“导入行待处理（行）”和“计划缺口待归因（份）”；“待人工匹配”只是导入行待处理的子集，不得与计划缺口混为同一级业务含义
  - 确认印数与源文件总数的差额必须按具体发货明细展示；客户暂停本期、停刊或取消寄送可登记无需发货，原因默认从“客户要求暂停本期发货 / 客户取消或停刊 / 本期确认无需寄送 / 其他原因”中选择；合寄不得登记为无需发货
  - 合寄分为 `twice_monthly_consolidation`（每月两次：当月前两期一批，剩余 2～3 期在最后一期一批）和 `month_end_consolidation`（整月 4～5 期在最后一期一批）；每条记录保存目标刊期、目标日期和批次，分别统计、分别展示
  - “马飞—库房留存”固定登记为“转库留存/库存入库”，不得登记为运单、无需运单、无需发货或任何合寄类型；计划份数记错归属时必须采用同一事务内的净额转移，转出与转入同时保存、总计划不变；合寄运单可按收件人分配到多个历史刊期
  - 历史“马飞—库房留存”必须按当期完整计划数量幂等补齐库存入库核销；旧“无需运单”导入行保留原始内容并标记为已忽略，批次匹配数与计划差异同步重算；检测到真实运单、包裹分摊或有效合寄记录时必须阻断自动转换并转人工核对
  - 新增无需发货记录必须选择本期具体发货明细并保存收件信息快照；历史无归属记录显示“待补充归属”，在补齐归属前可参与历史核销总量，但不得解释确认后计划差异
  - 计划对平、物理发货、核销完成是三个独立结论：例如确认 1,321 份、当前计划 1,320 份、已归因停发 1 份、实际寄出 1,320 份时，计划显示“计划已对平”，实际状态显示“核销已完成 · 部分发货”
  - 重新上传计划不得丢失已确认运单；历史清空造成运单行失去明细关联时，只能按唯一收件信息或“同名且拆分运单合计恰好等于唯一计划剩余份数”的条件恢复，不能唯一判断的必须转人工；已有发货或核销历史的明细禁止直接删除或整期清空
  - 人工忽略源文件行必须填写原因，原始行和原因继续保留用于审计
- **手动调整**：
  - 可新增、编辑、删除、批量更新ZTO-MF
  - 每次修改都会刷新与报数页对照的当前状态
  - 支持按出刊日期、期号、渠道、子渠道、签约公司、频率、运输方式、状态和姓名筛选

### 4.2 变动数据
每期需要手动输入。

| 类别 | 子类别 | 说明 |
|------|--------|------|
| 邮发 | 北京邮发（外埠） | 外地邮政订阅 |

**临时加印归属明细**：
- 临时加印总数可进一步分配到各部门（营报传媒、财经中心、中经未来、产经中心、其他）
- 每条明细包含：部门、加印数量、自留分发数量
- 快递数 = 加印数量 - 自留分发（自动计算）
- 所有明细行的数量之和 = 临时加印总数
- 自留分发不得大于对应明细的加印数量；临时加印总数为 0 时，所有归属、自留和快递数量必须归零
- 选择"其他"部门时可输入自定义名称

### 4.3 报数去向
每条报数明细都有固定的目的地/去向（`destination`），用于按接收方汇总和与ZTO-MF校验。

| 报数类别 | 去向 |
|----------|------|
| 邮发 / 北京邮发 | 北京市报刊发行局 |
| 报零 / 北京报零 | 北京市报刊零售公司 |
| 合订本 | 印厂 |
| 其他类别 | 中通物流公司 |

### 4.4 原始来源文件与后续调整

**凭证归档**：
- 每个来源文件保存原文件名、规范显示名、渠道、用途、来源日期、文件大小、SHA-256、上传人、识别状态和识别明细。
- 原始报数、月度报数、印前追加、确认后仅归档、追加订数、补损重发、冲减和已替换文件统一使用来源文件卡片展示。右侧来源栏应保证长规范名和原名完整换行；卡片统一提供规范名、原名、本期份数、关联刊期、用途、状态和下载入口。北京邮发按本市、外埠（含损失分摊）展示份数，北京报零按东部、西部展示份数，广州日报按订户、零售展示份数；成都杂志铺无分类时只展示本期数据。印前来源优先展示确认计入数，有人工分摊差异时并列保留原始识别数，确认后凭证展示凭证记录数；业务计算仍按用途分别影响印数、结算或补发。
- 文件保存时记录上传所在刊期。即使 OCR 未识别出明细、刊期无法解析或用户暂时关闭核对窗口，文件也必须留在该期并显示「待关联刊期 / OCR待核对」，且在处理完成前阻止确认印数。
- 文件卡片的「来源已人工确认」只表示原文件中的数字、刊期映射及用途已经人工核对，不等于对应刊期的印数已经确认。已确认来源与当前报数应逐项实时对比并显示差值。
- 规范名按来源自动生成，例如 `20260803_北京邮发_原始报数.pdf`、`2026年08月_成都杂志铺_月度报数.jpg`、`20260717_成都杂志铺_确认后凭证_3期共6份.jpg`。确认后凭证按唯一刊期计数，同一期的多个项目不能重复计为多期；刊期或份数未完整识别时省略统计，使用 `日期_渠道_确认后凭证.扩展名`，避免出现有歧义的“2期共0份”。
- 一个文件可关联一个或多个期号；每期页面都能下载原文件并查看本期对应的识别 / 调整项。
- 归档文件不存在或路径无效时显示「文件异常」，不得伪装为正常可下载文件。

**印前来源贡献台账**：
- 每条映射保存来源动作、印前 / 印后阶段、印数贡献、有效状态和被替换明细。右侧直接显示每份文件的角色 / 数量、渠道有效来源合计及其与当前印数的差额。
- 草稿期「追加」将新贡献与已有有效贡献相加；文件级「重新上传」只用新贡献替换所选文件贡献。例如基础 350、追加 15 时，重传基础为 340 后合计 355；重传追加为 20 后合计 370。
- 旧凭证不物理删除，标记为已替换；重新确认时服务端再次锁定并检查刊期状态，避免上传过程中报数已被其他人确认。

**成都后续补发**：
- 补发凭证可以跨月份映射到多个历史期，不要求和月度基础图片放在同一月份目录或只属于当前期。
- 每条调整必须选择一种业务含义：`追加订数`（增加结算并需要补发）、`补损重发`（只需要补发，不增加结算）、`冲减`（减少结算，不产生补发）。
- 页面分别展示锁定印数、结算数量、应补发、已补发和待补发；可登记已发数量、单号和发出时间。
- 死规则：已确认 / 已出刊期的 `report_entries` 不因后续凭证改变。调整只改变渠道结算和补发执行台账。
- 补发结算口径为：`结算数量 = 当期锁定的成都杂志铺印数 + 已确认结算调整`；最终结算包含符合规则的后续追加。

### 5.1 收件人信息
- **姓名**：收件人姓名或单位名称
- **电话**：联系电话
- **地址**：详细地址
- **类型**：对公/读者/样报
- **频率**：周/半月/月底
- **状态**：活跃/停发

### 5.2 三种类型

#### 对公（Business）
- **定义**：企业、机构、单位
- **示例**：某某公司、某某图书馆、某某研究所
- **特点**：通常订阅周期长，数量稳定

#### 读者（Reader）
- **定义**：个人订阅
- **示例**：张三、李四
- **特点**：订阅周期相对短，可能频繁续订或停订

#### 样报（Sample）
- **定义**：媒体、合作方、赠阅对象
- **示例**：某某报社、某某电视台、某某协会
- **特点**：通常不收费，用于宣传或合作

### 5.3 三种频率

#### 周（Weekly）
- **发送规则**：每期都发
- **适用场景**：核心订户、长期合作方

#### 半月（Biweekly）
- **发送规则**：每两周发一次（期号为偶数时发送）
- **适用场景**：预算有限的订户

#### 月底（Monthly）
- **发送规则**：月最后一期发送
- **适用场景**：仅需定期了解内容的订户

### 5.4 状态管理

#### 活跃（Active）
- 正常发送报纸
- 出现在发货明细中

#### 停发（Inactive）
- 暂停发送
- 不出现在发货明细中
- 可随时恢复

### 5.5 操作流程

#### 新增收件人
1. 点击"新增收件人"按钮
2. 填写姓名、电话、地址
3. 选择类型和频率
4. 保存后自动为 `active` 状态
5. 需要再添加订阅才能开始发送

> **地址自动补全**：输入地址时，系统会自动补全缺失的省/市/区前缀（如 `广州市白云区xxx` → `广东省广州市白云区xxx`），支持区县反查市级（如 `顺德陈村xxx` → `广东省佛山市顺德区陈村xxx`）。

#### 编辑收件人
1. 点击收件人列表中的"编辑"按钮
2. 修改信息
3. 保存

#### 停发
1. 点击"停发"按钮
2. 状态变更为 `inactive`
3. 后续不再生成发货记录

#### 恢复
1. 点击"恢复"按钮
2. 状态变更为 `active`
3. 下次生成发货时会包含该收件人

## 5C. 邮局投递管理

### 5C.1 功能定位
邮局投递与 ZTO-MF（中通）并列，是**一种投递方式**，但**按月**运作。邮局的数据是**投递记录层**（`PostalDelivery`），**不造订单、不进「订单管理 / 客户管理」**，避免与电商真实订单双算。一级菜单「邮局管理」下现有 **4 个二级菜单**：**投递明细**（`/post-delivery/deliveries`，纯台账 / 查询）、**待续投**（`/post-delivery/renewals`，核对订单邮局权益与现有投递段的缺口）、**订报转投**（`/post-delivery/subscription`，唯一产出「给邮局文件」——汇总表 / 分送表 / zip——的地方，给邮局的名单只来自这里）、**邮局工单**（`/post-delivery/tickets`，投诉 / 信息变更 / 回访三合一）。前端 `pages/PostDelivery.tsx` 包含投递明细、待续投、邮局工单 3 个 Tab；订报转投由 `SubscriptionGeneration.tsx` 独立承载。投递单位有则挂 `Partner(distribution)`、无则留空（不推断）。「收款发票」已从邮局管理迁至**财务管理**，作为其第 3 个 Tab「邮局收款」（页面 `pages/PostalReceipts.tsx`，接口 `/api/finance/postal-receipts/*`，前端 `api/finance.ts`）。

### 5C.2 源台账与手工维护
投递明细、邮局工单、收款发票各源台账均支持 Excel 导入，并提供页面内「新增 / 编辑 / 删除」。邮局工单按投诉 / 信息变更 / 回访类型使用不同导入模板（信息变更继续兼容历史《改地址》Excel），但物理上统一存入 `postal_tickets`。写操作需管理员权限。投递明细删除已无守卫，可直接删除（不再返回 409）。

前端正式布局统一为“页面标题与主操作 → 筛选 → 概览 / 列表 → 右侧详情抽屉”：投递明细按编号、收报人、地址、订阅、投递单位、订单来源分列，查看与编辑均使用抽屉；提供订阅状态直选（即将到期 / 投递中 / 待开始 / 已完结）。“即将到期”采用包含边界的 30 天窗口（止订日 `>= today` 且 `<= today + 30 days`，并且已开始），按止订日升序展示剩余天数、匹配订户 / 份数和最近到期时间。投递详情显示当前状态，并通过 `GET /api/postal/tickets?postal_delivery_id=...` 反查该订户的投诉、信息变更和回访，形成可点击的“服务处理”历史；管理员可在当前订户上下文直接新建三类工单，自动预填订户和投递信息。存在未解决投诉时必须提示重复投诉风险，并提供直达最早未解决投诉的处理入口。订户详情内打开任一服务记录时统一使用二级弹窗并保留详情抽屉供对照；从独立邮局工单列表打开时继续使用右侧抽屉，承载方式由入口层级决定而非工单类型。已应用的信息变更仍展示份数流向：差额未确认时以橙色“去向待确认”并标记“份数待核对”，已确认继续沿用原资料时以绿色“原信息保留”展示。邮局工单列表使用圆角工单卡片，字段依次为编号、收报人（姓名 / 电话）、工单类型、处理情况、登记日期、状态和操作；年度编号的数字部分统一补足 4 位。处理情况按类型显示投诉处理次数、信息是否已更新到投递明细或回访是否已记录，登记日期与状态独立成列，详情 / 编辑 / 删除均使用对齐的纯图标操作。订报转投以批次选择器和三步进度展示主流程；“重新上传来源”进入页面内工作区，依次完成上传、校验 / 汇总对比、设为有效，旧版本在确认前保持有效且确认后继续保留。上传阶段允许来源 A、B 各选择至多 20 份文件，来源 A 必填且至少 1 份，来源 B 可选；同一来源按选择顺序合并，跨文件重复订户仍按现有规则阻断并定位到文件。生成文件中的地区分送表按地区折叠展示。

历史工单导入需保留可追溯性：投诉按“年度编号＋接诉日期＋投诉内容”的出现次数判重，既保留源表中确实重复的多次投诉，又保证整表重导幂等；信息变更结合表头年度、修改日期年度、原姓名 / 电话和编号处理跨年及混合年度匹配；投诉与信息变更均在备注中记录源工作表和行号。

### 5C.3 邮局工单（投诉 / 信息变更 / 回访三合一）
投诉、信息变更（接口类型仍为 `address`，兼容历史《改地址》Excel）和回访三类工单合并为统一的「邮局工单」页，回访不再是独立菜单 / Tab，而是工单的一种类型，按类型筛选。

统一接口 `GET /api/postal/tickets` 从 `postal_tickets` 查询三类工单并返回 `TicketOut`（含类型、读者姓名与电话、关联、时间、摘要、状态、处理次数、应用状态、份数分配摘要与待确认份数），支持 `type`（`complaint` | `address` | `follow`）/ `year` / `status`（投诉）/ `applied`（信息变更）/ `recipient_pending` / `postal_delivery_id` / `search` 及数据库分页；`search` 模糊匹配姓名、编号和三类工单的电话快照，并忽略电话中的空格、连字符。接口另返回各类型计数和待确认收件人数。详情与 CRUD 统一走 `/api/postal/tickets[/{id}]`，处理时间线走 `/tickets/{id}/handlings`，应用变更走 `/tickets/{id}/apply`，剩余份数确认走 `/tickets/{id}/pending/resolve`，三类导入走 `/tickets/import/{type}/preview|commit`。

前端（`TicketsTab`，`api/postal.ts` 的 `listTickets` 等）：类型分段筛选（全部 / 投诉 / 信息变更 / 回访，带各类型计数）+ 圆角工单卡片（编号、收报人 / 电话、工单类型、处理情况、登记日期、状态、操作），列表不重复展示摘要内容。年度编号数字部分不足 4 位时仅在显示层左侧补零；处理情况按类型显示投诉处理次数、信息是否已更新到投递明细或回访是否已记录；日期与状态独立成列，详情 / 编辑 / 删除使用对齐的纯图标操作。`DeliveryDetailDrawer` 同样按 `postal_delivery_id` 查询统一工单，展示服务历史、重复投诉提醒和上下文新建入口；从订户详情打开三类工单统一使用二级弹窗，从工单列表打开继续使用详情抽屉。三类详情能力如下——
- **投诉**：真正的三态处理流程 `open`（待处理）/ `in_progress`（处理中）/ `resolved`（已解决），每次处理记入统一时间线表 `postal_ticket_events`（时间 / 处理人 / 处理过程 / 回访结果），处理次数每次 +1，状态由最新一次处理驱动，抽屉按时间线展示历次处理记录。投诉详情中的中通补发区按任务状态决定默认展开状态：零任务时收拢为单行“未使用”，隐藏说明、空状态和创建表单；存在任务时自动展开，并在标题汇总任务次数和状态。用户可随时手动切换，关闭详情后恢复由任务数据决定的默认状态。
- **信息变更**：变更前后姓名 / 电话 / 地址 / 份数对比 + 「应用变更」。「应用」把已填写的新信息更新到投递明细；若该读者挂了真实订单，则同步当前 `FulfillmentTarget`（=同步履约订单）；详情标注「已应用·已同步履约订单」或「已应用·仅名册」。部分份数变更时以 `copy_allocations` 保存每份去向，以 `unresolved_copies` 标记尚未闭环的差额；投递详情中的来源弹窗只读展示“已转出 + 原信息保留 / 去向待确认”，不在追溯页面修改原工单。本系统无独立客户资料表，订单收报人真值在 `FulfillmentTarget`。
- **回访**：手工登记明确区分「沟通内容」与「沟通结果」；旧 Excel 的「批次列头」仅保留导入兼容，不在手工表单展示。回访中发现投诉或信息变更时，可保存后继续创建一张或两张预填工单；同编号已有投诉时直接并入其时间线，不重复创建投诉工单。

## 6. 订阅管理

### 6.1 订阅类型

#### 新订（New）
- 首次订阅
- 记录新增订户

#### 续订（Renewal）
- 再次订阅
- 用于统计续订率、客户忠诚度

### 6.2 订阅属性
- **起始日期**：开始发送日期
- **截止日期**：停止发送日期
- **数量**：每期发送份数

### 6.3 有效性判断
订阅在以下条件下有效：
```
start_date <= publish_date <= end_date
```

超过 `end_date` 后，该订阅失效，不再生成发货记录。

### 6.4 数据分析支持
通过订阅记录可以分析：
- **续订次数**：某个收件人续订了几次
- **续订率**：多少订户选择续订
- **订阅周期**：平均订阅时长
- **客户价值**：累计订阅份数和时长

### 6.5 操作流程

#### 为新收件人添加订阅
1. 创建收件人后，点击"订阅"按钮
2. 选择类型："新订"
3. 填写起止日期和数量
4. 保存

#### 为已有收件人续订
1. 在收件人列表中点击"订阅"按钮
2. 选择类型："续订"
3. 填写新的起止日期（通常从旧订阅结束后开始）
4. 保存

## 9. 业务规则总结

### 9.1 期数管理
- 期号连续递增
- 休刊期不创建期数
- 每期状态：draft → confirmed → exported
- 确认后不可修改（除非手动改数据库）

### 9.2 报数逻辑
- 固定项自动填入
- 变动项必须手动输入
- 每条报数项都有去向：北京邮发→北京市报刊发行局，北京报零→北京市报刊零售公司，合订本→印厂，其余类别→中通物流公司
- 总印数 = 所有项之和（不含临时加印_自留等子分配项）
- 确认时比较"中通物流公司"报数合计与当期ZTO-MF合计，不一致时给出核查提示
- 确认前可多次保存草稿
- 原始来源文件永久独立于报数值保存；OCR 不直接覆盖数据，只有人工确认的基础值可以写入草稿
- 已出刊印数保持不变；成都后续补发通过独立调整项进入结算与补发台账

### 9.3 发货逻辑
- 休刊期不生成发货记录
- 仅为 `active` 状态的收件人生成
- 必须有有效订阅（在起止日期内）
- 频率必须匹配当期
- 数量来自订阅记录

### 9.4 订阅逻辑
- 新订和续订分别记录
- 订阅可重叠（系统取最新有效订阅）
- 过期订阅自动失效
- 支持同一收件人多次续订

### 9.5 Excel 导出
- 使用模板（如存在）或动态生成
- 所有文件密码保护
- 文件名包含期号
- 支持单独导出或合并导出

### 10.6 渠道结算（结构化周期与退报）

- 一条系统记录对应一张结算单。保存时自动生成不可编辑的系统编号：渠道使用 `JS-QD-YYYYMM-流水号`，个人使用 `JS-GR-YYYYMM-流水号`；外部平台单号独立保存、允许为空和重复。
- 结算对象类型区分**渠道/个人**；“代销/包销”统一称为**销售模式**，是否显示、选填或必填由合作渠道档案配置。北京报零配置为必填，普通渠道默认不适用且不保存销售模式，不增加“正常结算”等虚构选项。
- 结算周期使用开始/结束日期，单周结算允许两端选择同一天；日期不限制星期几，以外部结算单的实际期次日期为准。
- 有退报时填写可选的退报开始/结束日期和退报扣款；`应结金额 = 报款/结算总额 - 退报扣款` 由系统计算，允许形成负数结转。
- 结算方向分为**应收**和**应付**：应收显示我方开销项发票/已收款，应付显示对方开进项发票/已付款。
- 新增/编辑弹窗只维护结算对象、方向、周期、金额、附件和备注，不放置当前不可操作的开票、收付款或人工状态控件；保存后通过“查看详情”进入后续流程。
- 新建时可同时选择多份附件，每份文件独立显示并可修改类别；系统按文件名和扩展名推荐结算单、开票申请、发票或其他凭证。点击保存后，附件与结算记录一次性持久化；支持 PDF/JPG/PNG/XLS/XLSX，单文件不超过 20MB，并以 SHA-256 拒绝同单重复文件。
- 新增结算按“先上传凭证（可跳过）→ 自动识别 → 核对/补全基础信息 → 保存”的顺序展示，避免用户先填写全部字段后才发现附件可识别。多份结算单中只允许一份识别来源驱动表单回填，第一份结算单默认作为来源；需要切换时使用“改用此表识别”动作，不显示含义不清的“主结算单/已归类”标签。北京报零识别来源 `.xlsx` 支持识别供应商、外部单号、正常/退报期次和金额；识别默认只补空字段或上一次由识别填入的字段，已经人工填写的值必须保留并明确列出，不允许静默覆盖。识别状态、条数与告警必须紧贴对应文件显示，其他附件不共享结果，识别失败仍保存原文件。
- 新增/编辑弹窗沿用邮局工单的标题、状态、卡片分区和底部操作层级；基础信息在桌面端按三列紧凑排列，结算周期与退报周期各占半行并保持同宽，金额按三列排列，备注使用正常表单字号且独占一行。窄屏逐级降为两列和单列，不得在可容纳多列时把所有短字段强制逐项独占一行。
- 结算对象下拉必须区分加载中、接口失败和真实空数据：接口失败显示原因与重试入口，真实无渠道显示“先维护合作渠道”的引导，不得把请求失败伪装为“暂无数据”。
- 结算详情分区展示结算信息、附件、开票、收付款和操作记录。开票必须在专用操作中登记日期并上传发票，发票留存在系统且开票状态自动更新；收/付款通过专用操作按次累计登记。
- 开票状态和收付款状态分别保存、分别筛选，互不覆盖；兼容用的旧流程状态按实际动作派生，已结清优先于已开票。删除最后一份发票后回退未开票，但不改变已结清状态。
- 历史 `period` 自由文本和旧单附件接口继续兼容；新页面只写结构化日期字段。
